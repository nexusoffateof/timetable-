## Архитектурное решение, которое уже принято

Расписание живёт на двух уровнях — это то самое «самое важное решение
во всём проекте», и оно заложено в модель данных, а не прикручено сбоку.

```
template  →  «по понедельникам вторым уроком алгебра в 9В»
overrides →  «а 2 марта вместо неё информатика, тема — циклы»
days      →  «а 23 марта каникулы, уроков нет вообще»
```

Экран всегда показывает результат наложения. Отсюда следуют свойства,
ради которых всё и затевалось:

- правка одного дня не трогает постоянное расписание;
- правка постоянного расписания не стирает темы уроков — они принадлежат дате;
- замены, отмены и переносы времени хранятся отдельно и снимаются одним действием;
- в каникулы шаблон просто не разворачивается, а разовое занятие добавить можно.

Код: `src/lib/schedule.js` (наложение), `src/state/scheduleReducer.js` (правки).
Та же логика продублирована на стороне базы функцией `resolved_lessons` —
чтобы бот не пересчитывал её на JavaScript и два источника правды не разъехались.

## Этап 5. Supabase: база и авторизация

**Схема накачена и проверена на живом проекте** `Timetable-for-work-time`
(Postgres 17, eu-west-2) четырьмя миграциями: `timetable_tables`,
`timetable_rls`, `timetable_functions`, `timetable_harden_trigger_function`,
`timetable_revoke_anon`.

Файл `supabase/schema.sql` соответствует задеплоенному состоянию и остаётся
идемпотентным — им же поднимается второй проект, если понадобится.

Что внутри: таблицы, RLS-политики на каждой из них, функция сборки
расписания на дату и функция выборки напоминаний.

Ключи проекта лежат в `.env.local` (в git не попадает).

### Что осталось на этапе 5

База готова, клиент к ней ещё не подключён — приложение по-прежнему хранит
данные в localStorage. Порядок подключения описан ниже, в разделе
«Переезд с localStorage».

### RLS — не пропускать

Ключ Supabase лежит в браузере и публичен по своей природе. **Без политик
любой желающий вычитывает всю базу целиком.** Это самая частая дыра в проектах
на Supabase, и она открывается молча — приложение работает как ни в чём не бывало.

В `schema.sql` политики включены сразу, вместе с таблицами. Не «потом добавим».

**Как проверить, что политики действительно работают** (не «включены», а работают):

1. Зарегистрировать два аккаунта, завести в каждом разное расписание.
2. Зайти вторым и убедиться, что чужих уроков не видно.
3. Из DevTools второго аккаунта дёрнуть таблицу напрямую:

```js
const { data, error } = await supabase.from('subjects').select('*')
// должны прийти только свои строки, а не вся таблица
```

Проверено на этом самом проекте, двумя пользователями:

| Что пробовали | Результат |
|---|---|
| B читает звонки, предметы, уроки A | 0 строк |
| B делает прямой запрос `where user_id = A` | 0 строк |
| B вставляет строку с `user_id` учителя A | ошибка политики RLS |
| анонимный запрос без токена | отказ в правах, до RLS |
| B читает свой профиль | 1 строка, своя |

Линтер безопасности Supabase на схеме чист. Единственное оставшееся
замечание — INFO о том, что у `reminder_log` включён RLS без политик:
так и задумано, это полный запрет для клиента, таблицу пишет только cron
под `service_role`.

### Переезд с localStorage

Хранилище намеренно вынесено в один узкий файл — `src/lib/storage.js`,
у него три функции: `load`, `save`, `clear`. Компоненты про хранилище
не знают ничего.

Действия редьюсера один в один ложатся на таблицы:

| Действие | Таблица |
|---|---|
| `subject/add`, `subject/update`, `subject/remove` | `subjects` |
| `bell/*` | `bells` |
| `template/upsert`, `template/remove` | `template_lessons` |
| `override/upsert`, `override/remove`, `override/cancel` | `lesson_overrides` |
| `day/set`, `day/setRange` | `day_marks` |
| `settings/update` | `profiles` |

Практичный путь: сначала заменить `load`/`save` на чтение и запись всего
документа при старте и по изменению — приложение поедет на базе за вечер.
Потом, если понадобится, перевести отдельные действия на точечные запросы.
Обратный порядок обычно заканчивается неделей рефакторинга без работающего
приложения посередине.

Резервную копию перед переездом сделать через «Настройки → Данные →
Скачать копию»: тот же JSON заливается обратно, если что-то пойдёт не так.

### Нужны ли вообще другие пользователи

Честный вопрос. Если планнер для себя — авторизацию можно пропустить и

## Этап 6. Telegram: привязка аккаунта

Токен у `@BotFather`, две минуты.

Схема привязки — в базе уже есть таблицы `telegram_link_codes` и `telegram_links`:

1. На сайте кнопка «Подключить Telegram» → в `telegram_link_codes` пишется
   одноразовый код, живёт 10 минут.
2. Пользователь отправляет боту `/start КОД`.
3. Бот (под `service_role`, на сервере) находит код, проверяет срок,
   пишет пару `chat_id ↔ user_id` в `telegram_links` и гасит код.

**Токен бота живёт только в переменных окружения на сервере.** Всё, что попало
в код фронтенда, доступно любому, кто откроет DevTools. Токен в браузере =
чужой человек управляет вашим ботом. Переменная не должна начинаться
с `VITE_` — Vite подставляет такие значения прямо в бандл.

**Проверка:** привязать себя, попросить у бота расписание на сегодня.
Ответ приходит и он ваш.

## Этап 7. Напоминания по расписанию

**Код написан и покрыт тестами** — `api/reminders.js` плюс запуск через
`.github/workflows/reminders.yml`. Подробности: `docs/TELEGRAM.md`.

Постоянно работающий сервер не нужен. Нужен cron — и здесь есть подвох:
**на бесплатном тарифе Vercel cron разрешён не чаще раза в сутки**, а деплой
с расписанием `*/5` на Hobby не пройдёт вовсе. Поэтому рассылку запускает
GitHub Actions: минимум 5 минут, бесплатно. На платном тарифе Vercel можно
вернуться к его cron.

Задача раз в 5 минут дёргает `due_reminders()` под `service_role`, шлёт
сообщения и пишет отправленные в `reminder_log`.

Три классические ловушки закрыты прямо в функции — проверено на живом проекте:

**Часовые пояса.** Сервер живёт по UTC, учитель — нет. Функция берёт
`now() at time zone profiles.timezone`, то есть настенные часы конкретного
пользователя, и уже в них складывает дату урока со временем урока. Смещение
приходит из базы таймзон, поэтому перевод часов и «Москва +3» ничего не ломают.
Хранить смещение числом нельзя — сломается дважды в год.

Это же правило действует и во фронтенде: даты — строки `YYYY-MM-DD` в местном
времени, время — `HH:MM`. `Date.toISOString()` для дат не используется нигде,
он переводит в UTC и в Москве стабильно отдаёт вчерашний день для всего,
что раньше трёх ночи. Смотри `src/lib/datetime.js`.

**Дубли.** Cron ходит каждые 5 минут, окно предупреждения — 15. Без защиты
одно напоминание уйдёт трижды. `due_reminders` отсекает уже отправленные
по `reminder_log`, ключ — тройка «пользователь + дата + звонок».

**Выходные и каникулы.** Отмеченные дни отсекает `resolved_lessons`: шаблон
в них не разворачивается. Отменённые уроки отсеиваются по `status`.

### Как проверять, не дожидаясь утра понедельника

Не нужно сидеть до 8:30. Все сценарии проверяются за секунды подстановкой
времени урока относительно `now()` — готовые запросы есть в разделе выше,
логика уже прогнана на живой базе:

| Сценарий | Ожидание | Факт |
|---|---|---|
| урок через 14 минут при упреждении 15 | приходит | приходит, `minutes_left = 14` |
| урок через три часа | не приходит | 0 |
| то же напоминание второй раз | не приходит | 0 |
| каникулы | тишина | 0 уроков в выборке дня |
| урок отменён на эту дату | тишина | 0 |
| напоминания выключены в профиле | тишина | 0 |
| пользователь без привязанного Telegram | не падает | 0, без ошибки |

Проверку часовых поясов стоит описать отдельно, потому что она поймала бы
наивную реализацию. На сервере было **3 сентября, 20:53 UTC**, а у учителя
с таймзоной `Asia/Vladivostok` — уже **4 сентября, 06:53**. Разные календарные
даты. Функция взяла дату учителя и нашла урок; реализация «по UTC» искала бы
уроки не в том дне и молча ничего не прислала.

Отправку в Telegram оборачивать в try/catch поштучно: недоступность одного
чата не должна ронять всю задачу.
